# Zoo architecture

Zoo is a game first, but it must not become a second implementation of generic engine infrastructure that already has an authority elsewhere in this workspace.

The architectural goal is the smallest playable vertical slice built on the intended long-term foundations, not the smallest self-contained amount of code.

## Authority map

| Concern | Authority | Zoo responsibility |
| --- | --- | --- |
| Park rules, money, placement validity, guest/animal decisions, staff work, saves | `zoo-core` | Own the deterministic game semantics and stable game IDs. |
| Zoo-specific scene framing, orbit/zoom policy, mapping game-space state toward shared scene contracts | `zoo-scene` | Adapt Zoo state without becoming a generic renderer or camera-math authority. |
| Camera matrices, transforms, renderer-independent mesh/asset semantics, animation primitives, LOD, and the reusable concrete Three.js browser renderer | `moritzbrantner/3d-lab` | Supply Zoo scene data and interaction policy; consume the shared renderer instead of constructing a parallel renderer. |
| Generated/processed asset provenance, canonical asset catalog, reproducible 3D processing | `moritzbrantner/asset-tooling` | Declare Zoo asset intent and consume verified outputs. |
| Collision response, rigid-body motion, CCD, physical spatial queries | `moritzbrantner/physics-engine` | Integrate only where physical truth is part of gameplay; do not approximate engine behavior in React. |
| ECS storage experiments and benchmark evidence | `moritzbrantner/ecs-lab` | No direct runtime dependency. Reusable ECS functionality must first become an intentional shared foundation rather than being copied out of the lab. |
| Geographic/MapLibre map presentation and geo-data utilities | `moritzbrantner/maps` | No forced dependency for the current tile park. Reuse only a genuinely applicable data/spatial contract; Zoo owns its park-grid semantics. |
| React UI, touch/mouse/keyboard interaction, HUD/windows, and thin consumer glue | `apps/web` | Present authoritative state and translate user intent into commands. It must not own game balance, placement validity, generic rendering, camera projection math, or physics semantics. |

## Current correction

The browser presentation grew from an MVP into a local pseudo-3D engine: CSS perspective/3D transforms, local yaw/pitch projection policy, object billboard compensation, and a large `App.tsx` all accumulated in the product repository. That proved the game loop but created the wrong durable authority boundary.

The migration therefore proceeds upstream-first:

1. The missing orthographic/isometric-capable camera primitive was added to `3d-lab` rather than extending Zoo's CSS camera math.
2. `zoo-scene` is the thin Zoo-owned adapter over one exact pinned `3d-lab` revision. It owns park framing, free orbit, pitch bounds, zoom limits, pan clamping, and the mapping from a picked ground point to the park grid, while returning shared `three-d-camera` perspective matrices and unprojecting through shared `three-d-projective` inversion.
3. `3d-lab` now also owns the reusable concrete Three.js renderer. Zoo consumes it at the same exact accepted revision; React does not instantiate its own generic renderer.
4. The park view is one shared-renderer canvas. Terrain, fences, buildings, concessions, habitat furnishings, animals, guests, staff, litter, maintenance markers, and interaction overlays (hover, placement ghosts, selection) are all shared scene nodes composed by `apps/web/src/park-scene.ts`. The earlier transitional DOM tile/object layer, its MutationObserver reprojection, and the CSS pseudo-3D stylesheets have been removed. Static nodes (terrain, fences, buildings, and the surrounding scenery) are submitted as shared-renderer instance batches, grouped per unit primitive and 16-tile ground cell by `apps/web/src/scene-batching.ts`, so the park costs roughly a hundred draw calls instead of one per part; animated actors remain individual nodes.
5. Picking is renderer-side: ground/tile picks come from `zoo-scene` (shared inverse view-projection intersected with the park ground plane), and actor/building picks compare pointer position against anchors projected with the shared `createWorldProjector` helper. Final command validity remains a `zoo-core` decision.
6. Durable 3D assets move through `asset-tooling`; renderer-independent mesh/material/LOD semantics remain in `3d-lab`.
7. Path construction, habitat ownership, guest choices, welfare, economy, staff tasks, and other game-specific rules remain in `zoo-core`.
8. `physics-engine` is added only for interactions whose gameplay semantics require physical collision/motion truth. Tile occupancy and ordinary park pathfinding do not become physics problems merely because the game is rendered in 3D.

## Construction transactions

Construction is planned and committed in `zoo-core` (`crates/zoo-core/src/construction.rs`, #92). `evaluate_path_stroke`, `evaluate_concession`, `evaluate_habitat_rect` and `evaluate_demolition` return the exact tiles, price, affected objects, blocking tiles and rejection reason; the matching commands plan again against the current park, so a stale preview never spends or builds. One gesture is one all-or-nothing transaction: a path stroke is sent whole on release and Rust joins its points into a 4-connected line.

Undo/redo reverses construction only, through validated inverses: at most 16 transactions; undo refunds exactly what the transaction spent and redo charges it again with the same stable IDs; undo is refused once the construction has been used (guests or staff on a path, litter, sales, maintenance, animals, shelters, care work), leaving ordinary demolition. Demolition is free and is undoable only when it destroyed nothing irreversible. History ends with the in-game day so refunds always land in the ledger that holds the spending, is never saved (a load starts empty), and is replayable because undo and redo are recorded session commands. The browser only gathers gesture tiles, shows Rust's preview, and cancels on Escape, pointer cancel, lost pointer capture or a second finger.

Park circulation (#98) stays on the tile grid. Every path tile carries an access class, public or staff-only (save schema 10 makes every older path public), and remains its own route-graph node. One permission table decides who walks what: guests walk public paths and the entrance, and keepers, janitors and mechanics also walk staff-only paths; every path search takes its mover, so guests never cut through a service route and a viewpoint is always a public tile. `evaluate_path_stroke`/`build_path_stroke` take a brush width of 1 to 3 (a square on every stroke tile, extending right and down for even widths, clipped at the park edge) and an access class; `evaluate_plaza`/`build_plaza` fill a rectangle. Each is one transaction: grass becomes path at the catalog tile price, path of the other class is reclassified for free (refused under a guest who would end up on a staff-only tile), and undo restores both. Width adds real tiles; it never raises a single viewpoint's four-person capacity. Concessions need a public neighbour for customers; every adjacent path tile is a service point, and a mechanic uses the nearest one reachable by staff route (ties by row, then column), so a stand with a staff-only back keeps working when its public side is cut. Every path edit goes through `topology_changed`, which advances the session's topology revision and re-plans only the guest routes and janitor/mechanic assignments the edit broke; `diagnostics_json` reports `topology_revision` and `route_invalidations` beside `path_searches`. The access overlay grades public tiles by guest reach from the entrance and staff-only tiles by staff reach from the depot.

Land is purchasable inside the bounded scenario map (#99, `land.rs`; save schema 11 gives older parks no parcels, so they own their whole map). A scenario's `land` lists parcels with a stable slug ID, a title, a one-sentence trade-off, one or more rectangles, a price and an optional unlock (a scenario `Goal` plus its description); parcels may not overlap or cover the entrance or depot, and setup steps obey ownership like player construction. Every tile outside an unbought parcel is owned. Ownership is placement truth: path strokes and plazas, stands, new and reshaped habitats and service gates reject unowned tiles in the same plan their preview shows, naming the parcels and their price (`land_parcels` on the preview, plus the price the action would cost once the land is bought). `evaluate_land_purchase` quotes a selection (each parcel's price and status, the total and a quote token derived from them); `buy_land` plans again and refuses, spending nothing, an empty, unknown, repeated, owned or locked selection, a total the park cannot afford, or a quote that no longer matches. One purchase is one ledger line (`land_expense_cents`) and is final: it is not construction and never enters the undo history, and it changes no tile, route, ID or camera framing. The snapshot's `land` view lists each parcel's status (owned, available, unaffordable, locked), restriction, buildable and water tiles, path frontage and price per buildable tile, so the choices can be compared. The browser's Land tool tints parcels by that status and gathers the selection; unbought land always wears a muted tint, which is decoration only. The expansion plan is browser state that is never saved: finished path and habitat gestures in Plan mode are kept as gestures, re-evaluated by Rust against every snapshot and committed one by one through the normal commands, so planning never spends money or creates simulation objects.

## Management alerts and overlays

Park problems are `zoo-core` state (`crates/zoo-core/src/alerts.rs`, #94). After every command and every simulated minute Rust re-reads each alert condition (empty or low feed store, cut-off service gate, unstaffed habitat, late or missed scheduled care, low welfare, unsuitable group, destination guests cannot reach, broken-down or unserviced stand, crowded viewpoint, litter backlog, keeper without a zone) and keeps one alert per reason code and object, with severity, the tile of the cause, a suggested action and its first and last occurrence; a resolved condition or a removed object drops its alert. Alerts are saved (schema 4), so replay and reload agree. Overlays and the daily summary (`crates/zoo-core/src/overlay.rs`) are read-only views computed on request: `overlay_json(kind)` grades tiles for access, welfare, staff coverage, cleanliness, facilities or guest viewing and lists the problem objects, and the snapshot's `summary` carries today's numbers with the entities and ledger lines behind each. The browser re-reads the active overlay with each snapshot, never per frame, and only sorts, filters and lays out these values in the management workspace (`apps/web/src/ManagementWorkspace.tsx`).

Guest-comfort facilities are `zoo-core` state too (#101, `crates/zoo-core/src/comfort.rs`; save schema 12). Toilets, benches and litter bins are content-defined facilities with a `capacity` (cubicles, seats, or the litter a bin holds), built, undone, demolished and charged hourly upkeep through the same stand transactions and ledger lines. Guests accumulate a toilet need and lose energy; once a need crosses its threshold a walking guest picks, deterministically, the open facility whose public customer tile it can reach that has a free slot, then the shortest route, then the lowest ID. Choosing a free slot reserves it at once, so a slot is never double-booked; a guest who can reach only full facilities queues at the nearest for a bounded time and then gives up. Toilets empty the need after a short visit, and benches restore energy only for the minutes a guest sits. Every way a visit ends (use, giving up, demolition, a path cut, the guest leaving with a demolished habitat) releases the slot, and saves carry reservations and errands so a reload continues identically. A guest who finds nothing usable records the unmet need, which drives its thought, the `needs_toilet`/`needs_rest` complaints, the `toilet_demand_unmet`/`rest_demand_unmet` alerts (whose actions pick the toilet or bench tool) and the facilities overlay. Bins are used by explicit guest behaviour: a guest who has just bought something drops the wrapper in a bin with room beside its tile, or on the path. A toilet below its cleanliness line or a full bin raises one janitor service task; janitors serve it through the same oldest-first queue as path litter, walking to the facility's nearest staff-reachable service point, and the facility recovers only on arrival (`facility_needs_service` alerts an unanswered one). Toilets also wear and are repaired by mechanics like stands. The browser composes their look from primitives like the stands and shows Rust's occupancy, cleanliness, fill, service and unmet-demand values in the facility inspector and workspace.

Food and drink stands are staffed services in `zoo-core` (#102, `crates/zoo-core/src/stand.rs`; save schema 13). They reuse the comfort errand machinery: a guest's visit names the stand and the food or drink need it meets, and the stand's slots are the guests at its vendor windows. Each stand adds an open/closed switch, posted vendors (each serves one guest at a time, paid hourly with no hire cost), finite stock, a first-come-first-served queue of bounded length, and its own today and all-time ledger (sales, revenue, waiting time, lost sales by reason, stock, wage, upkeep and repair costs, contribution margin). Guests buy on impulse when passing a stand mildly hungry or thirsty, or detour once the need crosses its threshold, to the stand with the shortest expected wait they can reach and afford whose queue is not full (walking time plus the queue ahead per vendor, counting guests already on their way, then the lowest ID). Every minute each stand receives due deliveries, applies its one resupply policy (with automatic restocking on, a quarter of the stock or less orders a refill to full that arrives ten minutes later and is paid on arrival; restocking can also be ordered by hand), advances its windows, serves the queue in order and runs down waiting guests' patience. The sale at the end of service is atomic: stock, the guest's spending money, park income, the stand's ledger, the recovered need, satisfaction, wear and the wrapper the guest drops change together exactly once, or not at all. A stand that is closed, broken down (#57's mechanic condition; a worn stand also serves more slowly), without vendors, or sold out with nothing on order turns guests away with that distinct reason, a full queue, an unaffordable price or lost patience likewise, and each is counted as lost demand; demolition and path cuts end the errand without a sale. Queued guests do no route work. The `stand_unstaffed`, `stand_out_of_stock` and `stand_queue_full` alerts open the stand inspector, where the browser shows Rust's status, queue, speed, stock and figures and sends the open, vendor, restock and automatic-restocking commands.

Visitors come in groups (#103, `crates/zoo-core/src/visit.rs`; save schema 14 makes every older guest a group of one). The park's n-th arriving group draws its profile and size from n alone, so splitting groups never changes who comes next: families of three or four hope to see two nearby habitats and tolerate little crowding, enthusiasts (one or two) walk far for four habitats and their favourite species (one of the species on show when they arrive), and pairs of strollers sit between. A group arrives only when it can reach an attraction; its admission is one ledger line for all of its people and each person is a real guest record, so counts never include anyone who did not come, and arrivals are paced at the old rate per person. The group decides together whenever all its members have finished watching: needs (desperate toilet, thirst or hunger past the continue line, exhaustion), crowded minutes past the profile's patience, poor value or low happiness end the visit, as does reaching the visit goal; otherwise it scores every stocked, engaging habitat it has not seen from one breadth-first walk (interest from favourite species, appeal and welfare, minus the walk to the best #81 viewpoint, minus a penalty when every viewpoint is full), skips habitats beyond its walking tolerance and leaves with "no reachable attraction" when none remain. Members pick viewpoints in turn so a group spreads over free room. Errands to toilets, benches and stands stay individual (#101, #102): a member back from one rejoins the group's habitat. Ready members wait at most fifteen minutes for the rest; stragglers then carry on alone with the same profile, so nobody is held indefinitely and nobody moves except by walking. Crowding is a bounded game rule: more than six guests on one tile, or watching from a viewpoint over its `min(4, visible_animals * 2)` capacity, gives each a crowded minute, and the guest-viewing overlay marks crowded path tiles. Each guest who walks out is counted under its exit reason (satisfied, needs unmet, too crowded, poor value, no reachable attraction) with the state behind it; the snapshot's `visits` and the daily summary report them and the latest exits. `diagnostics_json` counts `itinerary_decisions` and `itinerary_candidates`; decisions run in the simulation tick and never in presentation.

Prices are the player's and every value decision is `zoo-core`'s (#106, `crates/zoo-core/src/pricing.rs`; save schema 16 opens older parks at their catalog's admission and each stand at its definition price). The park has one admission price per person, an open/closed gate and a price per food or drink stand, each validated as whole cents in a fixed range (fractions, NaN, infinities, negatives and out-of-range values are refused and change nothing). Each person of an arriving group carries one seeded budget: admission is paid out of it at the gate and the rest is the spending money stands charge, so admission and concessions share one spending state. A group that can reach an attraction comes to the gate and decides once, before anyone enters: the park's experience value is a base plus an amount per stocked, engaging habitat a guest can walk to from the entrance (more for welfare, at most six), so an unreachable habitat adds nothing and never blocks admission to reachable ones; each group pays at most that value times its profile's tolerance plus a seeded spread (families least, enthusiasts most). A closed park, a price above that limit or above a member's budget turns the whole group away: it pays nothing and nobody enters; otherwise every member pays once in one ledger line for the group (none when admission is free). Turned-away groups still take their place in the arrival sequence. A price at or below the experience value is fair and a bargain lifts arriving guests' value perception, while a premium lowers it, so dear tickets bring fewer guests who value their visit less. At a stand each guest pays up to the stand's authored reference price times its own seeded tolerance; above that it refuses (a "too dear" lost sale, less happiness and value, the need left unmet). The price is agreed when a vendor starts serving the guest and the completed sale charges exactly that, so a later price change never alters an agreed sale. The gate counts potential arrivals, admissions and rejections by reason per day and in total; the pricing view adds price complaints, poor-value exits, guests' mean value, income and profit, per-stand sales, complaints and contribution margin, and an admission forecast that replays the last 24 groups at the gate against a candidate price and states its assumptions. A marketing campaign costs a fixed amount once, runs for one day and brings groups to the gate at a fixed faster pace; only one runs at a time. The default ticket stays well below what any reachable park is worth, so default play admits every group (Decision 6.1.12).

A habitat is the row-major set of tiles one closed fence encloses (#95, `shape.rs`, `enclosure.rs`; save schema 5 converts older rectangles). The outline tool sends grid corners (corner `(x, y)` is the north-west corner of tile `(x, y)`, picked by `zoo-scene`); Rust joins them into unit fence edges, requires one closed loop that never revisits a corner, and derives the interior by row parity, so drawing direction and start never matter and holes, pinches and self-crossings cannot exist. Rectangles are a convenience over the same representation. `evaluate_habitat_outline`/`place_habitat_outline` build a new enclosure; `evaluate_habitat_reshape`/`reshape_habitat` move an existing habitat's fence while keeping its ID, animals, care, staff and gate (re-picked only when its segment leaves the fence). A reshape charges only for added tiles and new fence segments, refunds nothing it removes, rejects fences that hold fewer animals than live there or that a working keeper stands inside, and is undoable while the old fence still fits. Viewing spots, animal roaming and gate segments follow the enclosure's fence clockwise from its first tile. Every habitat is fenced with a content-defined fence type (`docs/content/catalog.md`): new habitats get the first one, reshapes price new segments at the habitat's own type, upkeep is per segment of that type, species with a higher minimum fence height cannot be adopted behind it, and `evaluate_fence_upgrade`/`upgrade_fence` rebuild the whole fence as another type at full price (save schema 6 moves the old implicit fence into content as the wooden rail).

Animals are individual records owned by their habitat (#96, `animal.rs`; save schema 7 turns older counts into records). Each has a park-wide stable ID that is never reused, its species, a player-editable name (`rename_animal`, trimmed, at most 24 characters), sex, life stage (every adoptee is an adult), arrival day, a cosmetic seed, its tile, its activity and its energy; a habitat's animal count is the length of its roster. Every two simulated minutes zoo-core walks each animal one tile through its enclosure towards a target chosen from the tiles clear of the fence, then rests it there; walking spends energy and resting restores it, and a tired animal rests longer. Choices hash the animal's own seed and decision counter, so other animals never change its identity, seed or path, and the renderer only interpolates the authoritative tiles. Guests count the animals visible from a viewpoint where they actually stand. Reshaping moves animals left outside the new fence to the nearest roaming tile. Arrival, renaming and departure emit `animal_*` domain events: the seam for later health, transfer and breeding work. Food, water, cleanliness, shelter, social and space fit stay habitat-wide and are shown beside each animal's own energy.

Compatible species share a habitat (#108, `mixed.rs`; save schema 17 makes each older habitat's one species and its welfare its only resident). A habitat's residents are its species in arrival order, each with an owned definition and its own welfare gauge; the habitat's welfare, welfare target, appeal, animal upkeep and feed use are derived from them weighted by their animals, so a departure changes them at once, even while paused. The catalog's `species_compatibility` profiles decide which pairs may mix (an unprofiled pair is unsupported; the built-in content pairs giraffes with zebras and refuses elephants with zebras). Each species' social group counts only its own animals; usable land, shelter and enrichment places, and the feed, water and cleanliness pool are shared by every resident that needs them; fence height, ground cover and water stay per species; one care schedule merges every resident's default categories and the largest crew. Adoption (one or a group of up to twelve, `adopt_group`), transfer between habitats (`transfer_animal`, keeping the animal's identity) and save import pass the same room, compatibility, fence and staffing rules; `evaluate_adoption` and `evaluate_transfer` preview the verdicts and the effect on space, shared places, feed use, upkeep and each species' welfare target for both habitats, and `rehome_animal` sends an animal to a partner zoo. React shows these previews and the resident groups; it holds no compatibility table or animal count of its own.

A habitat's layout is its environment (#97, `environment.rs`; save schema 9 turns the old shelter flag into a basic shelter object): sparse row-major terrain cells (a missing cell is level grass) with a surface (grass, sand, shallow or deep water) and a height step `0..=4`, plus up to eight one-tile shelters or enrichment items with park-wide stable IDs and owned copies of their content definitions. Everything is counted from the service gate's inside tile: land and shallow water are walkable, deep water never is, and neighbours more than one step apart are a ledge. The reached tiles are the animals' roam area and, minus water and furnished tiles, the space score's usable land; deep water counts when it touches reachable ground, and a furnishing counts only on a reachable tile. Each species' content requirements (ground cover share, shallow and deep water tiles, shelter and enrichment for every animal) become welfare parts with a weight, a score and an explanation; the welfare target is their weighted average (social group and space count double) and the habitat status names the first unmet one. `evaluate_habitat_terrain`/`paint_habitat_terrain`, `evaluate_habitat_elevation`/`set_habitat_elevation` and `evaluate_habitat_object`/`place_habitat_object` plan each edit on a copy and commit it whole: they refuse, spending nothing, to strand an animal or keeper, flood the gate tile or a furnished tile, put water above height 0, raise a fence-side tile, or leave neighbours more than two steps apart; repeating an applied edit is a free no-op. Reshapes must keep furnishings inside and fence-side tiles level, and drop terrain the fence gives up. Elevation stays a per-habitat game rule on the park grid (no bridges or stacked paths), and no physics query is involved. The renderer colours and lifts exactly these cells and draws the furnishings on their tiles; the cosmetic scenery keeps off them and never stands in for water or shelter, and the old decorative species pond is gone, so splashes come only from real shallow water.

Keeper care is scheduled, zoned and physical (`care.rs`, `zone.rs`; #133–#136, #104, save schema 15). Habitats own recurring care tasks copied from species defaults; each occurrence is one job keyed by habitat, category and due minute, with a one-hour grace before it is missed. Every minute the scheduler serves due jobs by priority, then oldest due, then ID, giving each the nearest free eligible keepers (same zone as the habitat's service gate, accepting the category, on shift) as one crew reserved together; there is no cross-zone borrowing. A feeding job for hungry animals reserves one feed crate at the depot (reserving never moves stock); its worker walks to the depot to collect it, carries it along staff-walkable paths through the service gate and then through the habitat's roam area to the job's care spot (feeding station at the centre, the far corner for cleaning, the first reachable shelter or enrichment item), where the crew works and the care is applied, the crate consumed and cleaning supplies booked once. Dispatched jobs reconcile with the world: a crew member moved out of the gate's zone, a gate moved out of the crew's zone, or a crew with no route once the grace hour has lapsed hands the job back (due again inside the grace hour, else missed), its reservation released and a carried crate walked back to the shelf; demolition does the same at once. Every job view exposes its phase, wait, remaining route and care spot, the depot view a care backlog (open, queued, blocked, oldest wait, recent outcomes, feed on shelf/reserved/carried, supply shortages), and `care_late`/`care_missed` alerts name the specific blocker and its fix. The park has one landmark depot, so "nearest reachable depot with stock" resolves to it or to none.

Utilities are simple capacity arithmetic in `zoo-core` (#113, `crates/zoo-core/src/utility.rs`; save schema 19 gives every older habitat normal priority, adds the built-in plants to the embedded catalog and leaves older species drawing nothing). Species content says how many units of pool water and climate control each animal draws (the built-in penguins one of each); a water pump or climate plant is a one-tile facility with a capacity and a coverage in path tiles, built beside any staff-walkable path. A plant serves a habitat only while it works and a staff path joins one of its service tiles to the habitat's service gate within its coverage: there is no pipe or cable routing, and furnishings, scenery and the renderer's lighting never supply anything. After every command and simulated minute Rust reallocates each utility in a fixed order (habitat priority high, normal, low, then habitat ID), each habitat drawing whole units from its reachable working plants nearest first then by plant ID; a plant never hands out more than its capacity, and every shortfall is stored with its reason (none built, not connected, failed equipment, overloaded) and fix. Plants wear at a quarter of a stand's rate through the existing maintenance tasks and mechanics; a failed plant supplies nothing and costs nothing to run until a mechanic repairs it (repair ledger line) or the player replaces it at its build price (its own ledger line, withdrawing the repair task). Operating cost is charged hourly for working plants on its own ledger line. Consequences are gentle (Decision 6.1.12): a shortage is an alert for its first hour, then a bounded welfare part (40 with no supply) for the species that need it, removed the moment supply returns. Habitat and plant inspectors, the utilities overlay and the shortage and overload alerts read the stored allocation; the browser only lays it out and sends priority and replacement commands.

## Dependency policy

Cross-repository dependencies must be pinned to exact accepted revisions. If a required shared contract is unavailable or incompatible, validation should fail closed rather than silently falling back to a second local implementation.

Both `zoo-scene` and the browser renderer consumer pin the accepted `3d-lab` revision. A pin moves only to another reviewed/accepted revision; it must not become a branch-tip dependency.

A local substitute is acceptable only when all of the following hold:

- the behavior is genuinely Zoo-specific, or the shared authority explicitly does not own it;
- the substitute does not establish a competing generic contract;
- the boundary and later migration cost are documented;
- deterministic/game-authoritative behavior remains in Rust.

## Rendering boundary

`zoo-core` emits stable game state and game-space coordinates. `zoo-scene` maps the presentation-facing parts into shared camera/scene semantics. `@moritzbrantner/three-d-renderer` from `3d-lab` owns concrete Three.js scene/GPU adaptation, including the WebGPU-camera to WebGL-depth boundary and reusable world-to-screen projection.

Camera orbit, zoom gestures, framing targets, and persistence are Zoo interaction policy. Projection/view math and concrete rendering are shared 3D infrastructure. Selection and placement intent may originate in the presentation layer, but final validity remains a `zoo-core` decision.

The park has no DOM interaction layer. `apps/web/src/ParkView.tsx` interprets mouse, wheel, keyboard, and touch gestures (one-finger pan, pinch zoom, twist rotate, two-finger vertical tilt) into `zoo-scene` camera calls and tile/actor picks, and translates tool gestures into the same `zoo-core` commands on desktop and phone.

Each park-view mount owns exactly one shared renderer. Unmounting disposes it and force-loses its WebGL context, so repeated load/dispose cannot accumulate contexts or GPU resources; `apps/web/scripts/renderer-lifetime-proof.mjs` remounts the view repeatedly and checks that live resources return to baseline. A catalog that fails the `zoo-core` content contract stops at a "Park could not start" screen with diagnostics export rather than booting a partial park.

Mobile and desktop inputs must converge on the same commands. Touch-specific gesture handling is presentation state and must not create a second rules path.

## Asset boundary

Zoo asset specifications and accepted generated outputs carry provenance through `asset-tooling`. Mesh/material/LOD processing remains owned by the corresponding `3d-lab` contracts and processors. Zoo may choose art direction and species/building requirements; it should not implement another generic asset pipeline.

The first asset-tooling asset at runtime is the scenery (#59 S2, #86): the rolling `zoo-scenery` release (`tree.mesh` round/pine/acacia, `bush.mesh` round, `grass.mesh` tuft, `rock.mesh` round/boulder, `static-glb-png-v1`). It surrounds the park and furnishes habitats with seeded, per-habitat-capped rocks, a boulder, grass tufts and the savanna acacia; these placements are cosmetic and never reach zoo-core. `assets/scenery/` pins the release tag, the tar SHA-256, the asset-tooling commit, Zoo's own copy of `export.ref.json` and the release lineage. `assets/effects/` pins the rolling `zoo-effects` release (dust/leaf/splash particle flipbooks) the same way, plus Zoo's copy of its descriptor (atlas layouts and burst presets). `bun run assets` (part of `build:web` and `dev`, `scripts/stage-asset-releases.ts`) downloads each tar, checks the pin and runs asset-tooling's `pack-asset-bundle.ts --verify --ref` at the pinned commit before staging the files and a provenance manifest into `public/zoo-scenery/` and `public/zoo-effects/`. The park view lowers the meshes with `three-d-renderer/static-glb`, requires each adapted resource key to equal the staged SHA-256, and fails closed otherwise; the Park manager panel shows both lineages under *Scenery credits*. The particle effects are cosmetic and optional: `park-effects.ts` turns presentation cues (a keeper `working` in a habitat → dust, a keeper or guest passing foliage → leaves, an animal stepping into a pond → splash) into bounded, cosmetically seeded `frame.effects.bursts` on the view's seconds clock, declares an atlas only while one of its bursts is live, sends `enabled: false` under `prefers-reduced-motion`, and never feeds game RNG or zoo-core. Moving to a new release means updating the pin, the `export.ref.json` copy and the lineage together; both pins and the Verify and Pages asset-tooling checkouts use the same commit.

## Physics boundary

The current management simulation does not need rigid-body physics for ordinary grid movement, placement, or guest pathfinding. When gameplay introduces physically meaningful interactions, Zoo should adapt stable Zoo entity IDs/state to `physics-engine` bodies and consume deterministic results back into the game simulation. React must never become the collision authority.

## ECS boundary

`ecs-lab` is evidence and experimentation, not the application runtime. If Zoo reaches a scale where an ECS materially improves simulation organization or performance, the reusable ECS contract should first be extracted into an explicit shared crate/repository, then adopted by Zoo. Copying a lab implementation directly into `zoo-core` would recreate the same ownership problem this architecture is intended to prevent.
